1. INTRODUCTION
--------------------------------------------------------------------------------
Multi-Agent SQL & Data Analyst is a natural-language business intelligence
tool. A user types a plain-English question about a sales database (for
example, "which 3 customers spent the most?") and receives, in one pass:

    - a SQL query that answers the question,
    - the verified result of running that query,
    - a chart built automatically from the result, and
    - a short written summary of the answer.

Instead of a single large prompt trying to do all of this at once, the system
is built as four small, single-purpose agents coordinated by a LangGraph state
graph. Each agent has one job, reads a shared state object, and writes its
output back into it for the next agent to use. This mirrors how a human data
team would split the work: someone writes the query, someone checks it runs
safely, someone charts it, someone writes up the finding.

The project's two distinguishing engineering ideas are:

    1. Self-correction. If the generated SQL fails to execute, the error is
       fed back to the SQL-writing agent, which gets up to two more attempts
       before the pipeline gives up cleanly instead of looping forever.

    2. Cross-run memory. When a retry succeeds, the (question, bad SQL,
       error, fixed SQL) is logged to a small JSON file. On every future
       question, the most similar past fixes are pulled back into the
       prompt -- so a mistake made once is not repeated on a different but
       similar question later, without needing its own retry first.

The database schema is introspected live from SQLite on every call rather
than hardcoded into a prompt string, so the SQL-writing agent cannot
hallucinate a column that does not exist, and the app can be pointed at a
different database with no code changes.

3. ARCHITECTURE
--------------------------------------------------------------------------------

                    ┌────────────────┐
   question ------> │  generate_sql  │  Agent 1 (LLM) -- NL question -> SQL
                    └───────┬────────┘  ▲
                            │           │ error, retries left (<= 2)
                            ▼           │
                    ┌────────────────┐  │
                    │  execute_sql   │──┘
                    └───────┬────────┘
                success     │      error, retries exhausted
                            │      ──────────────────────────┐
                            ▼                                 │
                    ┌────────────────┐                        │
                    │ generate_chart │  Agent 3 (logic)        │
                    └───────┬────────┘                        │
                            ▼                                 │
                    ┌────────────────┐                        │
                    │   summarize    │  Agent 4 (LLM)          │
                    └───────┬────────┘                        │
                            ▼                                 │
                           END  <──────────────────────────────┘
                            ▲
                            │  (cross-run, not part of the run above)
                    ┌────────────────────┐
                    │ error_memory.json  │
                    │  - logs (bad SQL,  │
                    │    error, fix) on  │
                    │    retry success   │
                    │  - feeds top-3     │
                    │    similar fixes   │
                    │    back into       │
                    │    generate_sql    │
                    └────────────────────┘

  Component responsibilities:

  generate_sql (agents/sql_generator.py)
    Writes one syntactically valid SQLite SELECT from: the live database
    schema, a short block of domain notes (e.g. "revenue = quantity * price"),
    the most similar past fixes from error_memory.json, and -- if this is a
    retry -- the exact error the previous attempt produced.

  execute_sql (agents/sql_executor.py)
    The safety boundary of the whole system. Rejects anything that is not a
    single read-only SELECT: whole-word blocks on DROP / DELETE / UPDATE /
    INSERT / ALTER / CREATE / TRUNCATE / REPLACE / ATTACH / PRAGMA, and
    rejects stacked statements (a second statement after a semicolon).
    Only after that check passes does it run the query against
    database/company.db. On error, increments retry_count and returns the
    error for generate_sql to see. On a retry that finally succeeds, calls
    error_memory.record_fix(...).

  generate_chart (agents/chart_generator.py)
    No LLM call. Inspects the pandas dtypes of the result: if there is a
    numeric column and a non-numeric column, plots the first of each with
    Plotly (bar for <=15 rows, line for more). If nothing sensible can be
    plotted (e.g. a single count), skips charting.

  summarize (agents/summarizer.py)
    Writes a 1-3 sentence plain-English answer from the result rows, using
    actual numbers from the data rather than a generic description.

  Shared state (agents/state.py)
    A single TypedDict (AgentState) is threaded through every node:
    question, sql_query, query_result, error, retry_count, chart_json,
    summary, plus last_failed_sql / last_failed_error (kept only long
    enough to let execute_sql log a successful fix to memory).

  Schema introspection (database/schema.py)
    Runs PRAGMA table_info and PRAGMA foreign_key_list against the live
    SQLite file on every call and turns the result into the text block
    generate_sql's prompt is grounded in. Nothing about the schema is
    hardcoded anywhere in the codebase.

4. WORKING -- STEP-BY-STEP EXECUTION WALKTHROUGH
--------------------------------------------------------------------------------
Worked example, computed directly from the bundled sample dataset:

  Question:
    "top 3 products by revenue"

  Step 1 -- generate_sql (Agent 1, LLM call):
    SELECT p.name, SUM(oi.quantity * p.price) AS revenue
    FROM order_items oi
    JOIN products p ON oi.product_id = p.product_id
    GROUP BY p.name
    ORDER BY revenue DESC
    LIMIT 3;

  Step 2 -- execute_sql (Agent 2, guardrail + run):
    Query passes the guardrail (single SELECT, no forbidden keywords, no
    stacked statements). Runs cleanly against company.db on the first
    attempt in this example, so retry_count stays at 0 and nothing is
    written to error_memory.json.
      Mechanical Keyboard  ->  $239.96
      Wireless Mouse        ->  $99.95
      Webcam HD              ->  $90.00

  Step 3 -- generate_chart (Agent 3, logic only):
    3 rows, one text column (name) and one numeric column (revenue) ->
    bar chart, "revenue by name", serialized to chart_json.

  Step 4 -- summarize (Agent 4, LLM call):
    "The top 3 products by revenue are the Mechanical Keyboard ($239.96),
    Wireless Mouse ($99.95), and Webcam HD ($90.00)."

  Step 5 -- Streamlit renders the final state:
    app.py reads result["summary"], result["sql_query"], result["query_result"],
    and result["chart_json"] out of the returned AgentState and displays them
    as: an answer paragraph, an expandable SQL code block, a data table, and
    an interactive Plotly chart.

  Failure path (not hit in the example above, but built in):
    If Step 2 raises a sqlite3.Error, execute_sql sets state["error"] and
    increments retry_count. should_retry() routes back to generate_sql,
    which now also receives the failed SQL and the exact error message and
    tries again -- up to 2 times. If the 3rd attempt still fails, the graph
    routes straight to END and app.py shows: "Couldn't get a working query
    after retries: <error>". If a retry DOES succeed, execute_sql logs the
    (question, bad SQL, error, fixed SQL) to error_memory.json before
    continuing to generate_chart.

7. HOW TO RUN IT
--------------------------------------------------------------------------------
  1. Create a virtual environment and install dependencies:
       python -m venv venv
       venv\Scripts\activate          (Windows)   |   source venv/bin/activate (macOS/Linux)
       pip install -r requirements.txt

  2. Configure the LLM backend:
       cp .env.example .env
       - OpenAI: leave LLM_PROVIDER=openai, paste a key into OPENAI_API_KEY
       - Ollama (free, local): set LLM_PROVIDER=ollama, install Ollama, then
         run: ollama pull llama3.2:3b

  3. Create the sample database:
       python database/init_db.py

  4. Launch the app:
       streamlit run app.py
       (opens at http://localhost:8501)

  Sample questions:
       "What were total sales by product category?"
       "Which 3 customers spent the most?"
       "How many orders came from Ireland?"

8. LIMITATIONS
--------------------------------------------------------------------------------
  - No automated tests yet -- the guardrail's keyword blocking is unverified
    by CI; a tests/ folder proving it rejects DROP/DELETE/etc. is a known gap.
  - Small local models (llama3.2:3b) are noticeably weaker than GPT-4o-mini
    at multi-join or aggregation-heavy questions -- expect more retries and
    occasional give-ups in Ollama mode.
  - Single SQLite file, single user: no authentication, no concurrent-write
    handling, not designed for multi-tenant use.
  - error_memory.py ranks past fixes by raw word overlap between questions,
    not semantic similarity (embeddings) -- adequate at the current scale of
    a demo fix log, would need revisiting at a much larger scale.
  - The chart agent only ever plots the first numeric column against the
    first non-numeric column; multi-series or multi-metric results are not
    charted specially.
